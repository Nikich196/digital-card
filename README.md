# Digital card — GraphQL backend

Цифровая визитка: GraphQL-API, отдающее профиль, навыки, опыт работы и проекты.

Стек: **TypeScript · NestJS · Prisma · PostgreSQL · GraphQL (Apollo) · Docker**.

**Развёрнуто и работает:** https://digital-card-eight-ochre.vercel.app

На главной — консоль запросов прямо в браузере, четыре готовых примера
(полная визитка, поиск по slug, состояние сервиса, ошибка «профиль не найден»).
Эндпоинт — `POST /graphql`. База: PostgreSQL в eu-central-1, функция вынесена
в тот же регион, полная выборка со всей вложенностью укладывается в ~220 мс.

---

## Быстрый старт

```bash
docker compose up --build
```

Одна команда поднимает PostgreSQL и приложение. Контейнер сам применяет миграции
и заполняет базу, отдельных шагов не нужно.

Дальше открыть **http://localhost:3000/graphql** — там Apollo Sandbox.

Проверочный запрос:

```graphql
query {
  profile {
    name
    headline
    skills {
      name
      category
      level
    }
    experiences {
      company
      position
      startedAt
      isCurrent
      achievements {
        text
      }
    }
    projects {
      name
      url
      stack
    }
  }
}
```

### Без Docker

```bash
cp .env.example .env      # указать свой DATABASE_URL
npm ci
npx prisma generate
npm run db:setup          # migrate deploy + seed
npm run build && npm run start:prod
```

## Решения, которые я принимал, и почему

### Слои

```
GraphQL resolver  →  service  →  Prisma
```

Резолвер только оркестрирует: спрашивает у сервиса корневой объект и отдаёт
вложенные поля загрузчикам. **Prisma в резолверах не вызывается ни разу** —
иначе слой представления начинает знать про схему базы, и заменить хранилище
или переиспользовать логику в другом транспорте становится нельзя.

Каждая сущность — отдельный модуль Nest (`link`, `skill`, `experience`,
`project`, `profile`) со своим сервисом. Модуль `profile` — единственный, у кого
есть резолверы; остальные предоставляют пакетные выборки.

### Вложенные данные и N+1

Это главная инженерная проблема задачи, и она решена явно.

Схема нормализована: профиль → опыт → достижения, то есть **два уровня
вложенности**. Наивная реализация на запрос

```graphql
profile { experiences { achievements { text } } }
```

сделает 1 запрос за профилем, 1 за опытом и **по одному за достижениями каждой
должности**. На двух должностях это незаметно, на пятидесяти — деградация.

Поэтому вложенные поля резолвятся через `@ResolveField` + **DataLoader**
(`src/common/dataloader`). Загрузчики создаются **на каждый HTTP-запрос** в
фабрике контекста GraphQL: кеш загрузчика, переживший запрос, отдавал бы
устаревшие строки.

Фактический результат — по одному SQL-запросу на коллекцию:

```
1 FROM "public"."profiles"
1 FROM "public"."experiences"
1 FROM "public"."achievements"
1 FROM "public"."skills"
1 FROM "public"."projects"
1 FROM "public"."links"
```

Проверить самому:

```bash
LOG_QUERIES=true npm run start:prod
```

и выполнить запрос — в лог попадёт каждый SQL.

`groupByKey` (`src/common/dataloader/group-by.ts`) существует потому, что
DataLoader обязан вернуть ровно один элемент на каждый запрошенный ключ и в том
же порядке, а пакетный запрос приходит плоским списком.

### База

Prisma, PostgreSQL. Ключевые решения по схеме:

- **`slug` у профиля уникален.** На него опирается идемпотентность сида.
- **Достижения — отдельная таблица**, а не массив строк в `experiences`.
  Так появляется второй уровень вложенности в GraphQL, у каждого достижения
  есть свой порядок, и его можно адресовать отдельно.
- **`finishedAt` nullable**, флага «текущая работа» в базе нет. `isCurrent`
  вычисляется в резолвере: одно состояние хранится в одном месте, рассинхрона
  быть не может.
- **Составные уникальные ключи** (`profileId + name` у навыков, `profileId +
  company + position` у опыта) — дубли отсекаются базой, а не приложением.
- **Индексы под реальные выборки**: `(profile_id, position)` для сортируемых
  коллекций, `(profile_id, started_at)` для опыта.
- Каскадное удаление на всех связях: профиль удаляется целиком и без сирот.

### Инициализация и наполнение

`docker-entrypoint.sh` перед стартом приложения выполняет `prisma migrate
deploy` и `prisma db seed`. Обе операции идемпотентны: миграции пропускают
применённое, сид делает `upsert` по `slug` и переписывает связанные записи в
одной транзакции. Контейнер можно перезапускать сколько угодно.

Данные лежат в `prisma/data/profile.json` — **отдельно от кода**. Обновить
визитку значит поправить JSON, а не лезть в скрипт.

### Конфигурация

Переменные окружения проверяются схемой Joi при старте (`src/config`).
Кривой `DATABASE_URL` роняет приложение сразу, а не превращается в непонятную
ошибку на первом запросе.

### Docker

Multi-stage сборка: в финальный образ не попадают ни исходники, ни dev-зависимости.
Процесс работает от непривилегированного пользователя `node`, точка входа
обёрнута в `dumb-init` для корректной обработки сигналов. У postgres в compose
есть healthcheck, приложение стартует только после него.

## Структура

```
prisma/
  schema.prisma          модель данных
  seed.ts                идемпотентный сид
  data/profile.json      содержимое визитки
  migrations/            SQL-миграции
src/
  config/                валидация окружения
  common/prisma/         подключение к базе
  common/dataloader/     пакетные загрузчики, решение N+1
  profile/               запрос profile + резолверы вложенных полей
  link|skill|experience|project/
                         модели GraphQL и пакетные сервисы
```

## Что бы я сделал дальше

Задача этого не требовала, но в реальном проекте следующим шагом были бы:
ограничение глубины и сложности запроса (защита от дорогих вложенных запросов),
пагинация коллекций по курсору, кеш на уровне ответа и e2e-тесты на схему.
